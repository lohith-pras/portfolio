# IoT Security Project

[View on GitHub →](https://github.com/lnlohith/iot-security-project)

A security audit and hardening project for a fleet of ESP32-based smart home sensors. The project covered the full attack surface: firmware extraction via physical UART, credential capture from unencrypted MQTT traffic, and replay attacks on the cloud API. Mitigations were implemented and verified with a second red-team pass.

## Phase 1
Threat modeling and attack surface analysis. Built a threat model using STRIDE, mapping physical access, network, and cloud attack vectors. Identified six high-severity issues, including plaintext credential storage in flash and absence of certificate pinning on the HTTPS client.

## Phase 2
Penetration testing and vulnerability scanning. Dumped firmware via UART (no secure boot enabled), extracted hardcoded Wi-Fi credentials and API tokens, intercepted MQTT traffic on the LAN, and demonstrated a full command replay attack on the cloud endpoint. The mutual TLS (mTLS) setup below was the target hardened architecture — replacing the original shared-token scheme.

```cpp title="secure_firmware.cpp"
#include <WiFiClientSecure.h>
#include <HTTPClient.h>

const char* ROOT_CA_CERT = "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----";
const char* CLIENT_CERT  = "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----";
const char* CLIENT_KEY   = "-----BEGIN RSA PRIVATE KEY-----\n...\n-----END RSA PRIVATE KEY-----";

WiFiClientSecure client;

void setup_secure_connection() {
    // Load root CA and client certificates/keys for mutual TLS (mTLS)
    client.setCACert(ROOT_CA_CERT);
    client.setCertificate(CLIENT_CERT);
    client.setPrivateKey(CLIENT_KEY);

    HTTPClient http;
    if (http.begin(client, "https://secure-iot-gateway.local/api/telemetry")) {
        http.addHeader("Content-Type", "application/json");
        int httpCode = http.POST("{\"status\":\"healthy\",\"firmware_ver\":\"1.0.4\"}");
        if (httpCode > 0) {
            Serial.printf("[mTLS] Status reported: %d\n", httpCode);
        }
        http.end();
    }
}
```

## Phase 3
Mitigation implementation and final report. Enabled Espressif secure boot and flash encryption, replaced shared API tokens with per-device mTLS certificates, and locked the UART interface. The final red-team pass confirmed all six high-severity issues were closed.

## What I'd Do Differently

- **Hardware-accelerated cryptography from day one**: The software-only TLS library I used on the ESP32 caused a significant current draw spike during the TLS handshake — degrading battery life by approximately 40% in sleep-wake duty cycles. The ATECC608A crypto co-processor was available on the target BOM and supports hardware-accelerated elliptic curve cryptography. Using it from the start would have offloaded the expensive crypto operations off the main core and kept current consumption within spec.
- **Mandate mTLS with individual device certificate enrollment from the start**: The original shared API token architecture was the root cause of several critical vulnerabilities. Physical access to any one device — or a single token leak — compromised the entire fleet. Had the threat model mandated per-device mTLS certificates enrolled at manufacturing time (even via a simple factory provisioning script), the entire class of credential theft and replay attacks would have been eliminated structurally rather than patched after the fact.
- **Secure boot and flash encryption during early hardware validation, not as a late hardening step**: Enabling secure boot and flash encryption late in the project required re-flashing every device with a different partition scheme and invalidated our existing OTA update toolchain. Locking down the physical interface and enabling full flash encryption at the first hardware bringup — when it's straightforward — would have saved significant remediation effort and prevented the firmware extraction vulnerability we demonstrated in Phase 2.
